# Support and validation

Validated on October 15, 2026 with Node 24.19.0, Mineflayer 4.39.0, minecraft-data 3.117.0 and Mojang's checksum-verified vanilla Java **1.21.11**, protocol **774**, using Java 21.0.12.1. The controlled server binds to loopback, uses a disposable flat world and fresh offline test accounts, and is stopped by the runner. Results are recorded in [validation.json](validation.json); this is current-instance evidence, not a production deployment or restored-cloud-task check.

Run `npm test`, `npm run check`, `npm run voice:check`, and, after explicit EULA acceptance/preparation, `npm run test:server`. The unit suite currently contains **33 passing tests** (including protocol/data compatibility, the mandatory `player_loaded` feature flag, v7 schematic validation/legacy rejection and conservative 1.21.11 equipment cooldowns); none are intentionally disabled or skipped. The dependency audit currently reports zero known vulnerabilities. A compatible CJS `uuid` 11.1.1 override removes the older transitive UUID bounds-check advisory; official Microsoft account login remains a separate live check.

Survival tick CPU time is measured by the integration runner and recorded in validation.json. This demonstrates the controlled fixture, not a hard real-time guarantee under arbitrary host load. No live AI/Discord request is on the survival critical path; planner and bulk audio conversion use workers. The combat fixture includes unresolved simulated service promises but no real remote AI/Discord connection. The zombie and creeper fixtures use `NoAI`, so these checks verify deterministic response, ordinary attacks/cooldowns and retreat, not victory against every moving mob or an exploding creeper.

## Explicit unsupported behavior

- Guaranteed unattended survival from any naked spawn, long-term food independence, automatic farms/replanting, animal hunting, smelting/cooking, enchanting, complex crafting chains, potion use, shield/ranged combat and provoked neutral-mob combat are unsupported. Current food support is safe inventory consumption and bread crafting at an approved table; limited foraging selects visible mature wheat, logs and exposed stone within reach when autonomous mining is explicitly enabled. Equipment uses available ordinary armor/tools. No exploration to locate hidden ores or privileged world information occurs. Copper armor is recognized by the equipment heuristic. Ordinary spear/mace melee uses conservative delays; spear lunging, mace smash strategies, new-mob tactics and riding/taming mechanics are not implemented or live-validated.
- Automatic mining and building default off. Bootstrap/table placement and shelter construction require the corresponding owner policy, permitted material access, an approved table coordinate and safe nearby terrain. Shelter uses 23 cobblestone blocks, an ordinary open entrance, reachable supports, normal jumps and bounded viewing-position changes. It has no door or lighting and is not guaranteed mob-proof. Missing supplies, blocked terrain or exhausted survey budget require owner intervention; it does not demolish obstructions.
- Autonomous swimming, sophisticated lava rescue, scaffolding towers, parkour, Nether/End travel, arbitrary teleportation, world-seed queries, x-ray resource searches, exploits, anti-cheat evasion, privileged commands, sleeping and PvP are unsupported. Navigation avoids known hazardous blocks/fluids and long drops. Escape can fail when no safe walkable route exists; the bot stops rather than inventing a bypass.
- Death recovery allows one respawn request per death, a short timeout, at most the configured death budget (default three), and at most 60 seconds/32 blocks of known safe return. It never guarantees retrieval of every dropped item. Death counts reset on a manual process restart; there is no automatic reconnect.
- Schematics must be **litematic v7/subversion 1, MinecraftDataVersion 4671**. Legacy v6/3700 exports and other data versions, rotations/mirroring, block properties/orientation/waterlogging, entities, tile/block entities, scheduled ticks, stairs, slabs, fences, doors, gravity blocks, fluids, redstone and other non-whitelisted types are rejected. Whitelisted stateless full cubes are ordinary planks, stone/cobblestone, dirt, glass, bricks/stone bricks, sandstone, terracotta, wool/concrete colors and approved crafting tables.
- Parser limits: 2 MiB input, 8 MiB inflated NBT, 16 regions, 128 cells per dimension and 50,000 total region cells. Build execution is further limited to the smaller of 512 non-air blocks or the configured action budget (default 500), and a fully visible surveyed site within six blocks for preflight/final reconciliation. Placement itself uses a conservative 4.5-block reach and the actual visible support face. Large, occluded or tall builds can pause/reject instead of placing blindly. Air entries do not authorize demolition. Support columns are at most eight blocks deep and 128 added blocks. Supports remain in place until individually mined with the destroyer role and area permission.
- Schematic uploads are held in memory (maximum four) and must be uploaded again after restart. Checkpoints persist; re-running at the same origin/dimension rechecks actual world state. Finishing a build whose blocks are no longer all visible requires another survey. Existing correct blocks do not bypass placement-area/actor permissions when actions are needed.
- Only approved single chests and barrels support transfer actions. Double/trapped chests and other container types are rejected. A crafting table must be independently allowlisted. There is no Discord arbitrary container-transfer command; the executor's bounded transfer API is available for future explicitly scoped tasks.
- Conversation can propose status, staying, movement and crafting. Destruction requires the explicit `/mine` command; construction requires `/build`. There is no arbitrary AI code/tool execution or conversational policy editing. These structural controls prevent privilege escalation from prompt injection; they do not guarantee that every allowed model proposal is sensible.
- Voice receives only authorized operators in approved channels after policy opt-in. At most two utterances are admitted concurrently; clips over 12 seconds are dropped, transcripts are capped, and responses are bounded. Recognition may misunderstand speech. Interruption cancels pending speech/planning responses; use `/cancel` or an independent stop to interrupt a Minecraft task already issued. Discord audio reception is not officially documented/stability-guaranteed by Discord, as the upstream library documents.
- Live Discord voice requires usable direct secret injection and raw UDP/WebSocket access. HTTPS proxy secret placeholders/domain lists alone are insufficient evidence. There are no claims of live DAVE success, production readiness, cloud publication or restoration in a new task.
